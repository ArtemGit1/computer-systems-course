# Lab 04: Процеси та системні виклики

## Мета роботи

Метою роботи було дослідити, що відбувається після запуску executable: як ОС представляє процес, як програма взаємодіє з kernel, як `fork()` створює child process, як `exec()` замінює програму процесу та як `wait()` збирає результат завершення child.

Роботу було виконано в Linux-середовищі GitHub Codespaces. `/proc` та Linux-утиліти використовувалися як експериментальні засоби для вивчення понять program і process, PID/PPID, system calls, адресних просторів, станів процесу, zombie та моделі `fork → exec → wait`.

## Середовище та компіляція

Роботу було виконано в терміналі VS Code, підключеному до Codespace. Codespaces надає Linux-контейнер, який використовувався як середовище виконання лабораторної; це не є твердженням про операційну систему локального комп'ютера. Наведені приклади спостережень отримано в цьому Codespace (Linux x86-64, GCC 13.3, `strace` 6.8).

Для перевірки середовища було виконано:

```sh
cd labs/lab04-system-calls
gcc --version
strace --version
```

Для компіляції прикладів було використано цикл:

```sh
for source in *.c; do
    gcc -Wall -Wextra "$source" -o "${source%.c}"
done
```

У середовищі були доступні `gcc` та `strace`. До репозиторію додано вихідні файли; executable створювалися лише для локальної перевірки прикладів.

## 1–3. Program, process і `/proc`

Файл `process_info.c` було скомпільовано й запущено. Програма вивела PID та PPID, після чого залишалася активною протягом 30 секунд:

```sh
gcc -Wall -Wextra process_info.c -o process_info
./process_info
```

Під час роботи програми її процес було досліджено з іншого terminal за допомогою команд:

```sh
ps -p PID
ls /proc/PID
cat /proc/PID/status
tr '\0' ' ' < /proc/PID/cmdline
readlink /proc/PID/exe
head -n 20 /proc/PID/maps
```

У запуску в Codespaces програма мала стан `S, а `/proc/PID/exe` вказував на executable `process_info`. Записи `Pid` і `PPid` у `status` збігалися зі значеннями, надрукованими програмою. Точні PID, PPID та адреси mappings змінюються між запусками.

`/proc/PID` — не сам процес, а доступне через procfs представлення його поточного стану. Після завершення процесу відповідний каталог зникає. До запуску executable є файлом; один і той самий файл, запущений окремо кілька разів, утворює різні процеси з різними PID.

Для порівняння кількох процесів `process_info` було запущено тричі одночасно:

| Instance | PID | PPID |
| :--- | ---: | ---: |
| Process 1 | 7223 | 7222 |
| Process 2 | 7224 | 7222 |
| Process 3 | 7225 | 7222 |

У цих трьох запусках було отримано різні PID і однаковий PPID. Під час повторного запуску числові значення будуть іншими.

Executable є файлом із програмним кодом; process — запущеним екземпляром із власним PID, станом і адресним простором.

## 4–5. System calls: `printf`, `write` та `strace`

```sh
gcc -Wall -Wextra hello.c -o hello
./hello
strace -e write ./hello
```

У trace з Codespaces суттєвий фрагмент виглядав так:

```text
write(1, "Hello from process!\n", 20) = 20
```

`1` — файловий дескриптор stdout, `20` — кількість переданих bytes, а результат `20` означає кількість записаних bytes. `strace` дає змогу спостерігати системні виклики, які доходять до kernel.

У `output.c` було порівняно два інтерфейси:

```sh
gcc -Wall -Wextra output.c -o output
strace -e write ./output
```

Під час запуску з перенаправленим stdout спершу з'явився прямий виклик `write()` програми, а потім `write()`, виконаний після скидання буфера `printf()`:

```text
write(1, "Output using write\n", 19) = 19
write(1, "Output using printf\n", 20) = 20
```

`printf()` — функція стандартної C library з форматуванням і буферизацією. `write()` — POSIX API, що запитує запис байтів через kernel. Не кожен `printf()` відповідає одному системному виклику `write()`: бібліотека може накопичувати або об'єднувати дані. Порядок виводу також може залежати від буферизації.

## 6–8. `fork()` і незалежність пам'яті

```sh
gcc -Wall -Wextra fork_basic.c -o fork_basic
./fork_basic
```

До успішного `fork()` працював один процес, після нього — два: parent і child. Виклик повернув PID child у parent та `0` у child; помилка позначається `-1`. Обидва процеси продовжили виконання з наступного рядка, але пройшли різні гілки.

Порядок виведення рядків parent і child не гарантувався. У `fork_basic` parent міг завершитися до того, як child надрукував свій PPID; у такому разі child міг бути перепризначений іншому батьківському процесу.

Для дослідження незалежності адресних просторів `fork_memory.c` було скомпільовано й запущено:

```sh
gcc -Wall -Wextra fork_memory.c -o fork_memory
./fork_memory
```

Було отримано результат такого вигляду:

```text
Before fork: value=100, address=0x...
CHILD:  PID=..., value=200, address=0x...
PARENT: PID=..., value=300, address=0x...
```

Числові адреси можуть збігатися в parent і child, але зміни `value` незалежні: child отримав `200`, parent — `300`. Після `fork()` кожен процес працює зі своїм логічним адресним простором; реалізація ОС може відкладено копіювати фізичні сторінки за допомогою copy-on-write.

Створення процесів було досліджено за допомогою `strace`:

```sh
strace -f -e trace=process ./fork_basic
```

Опція `-f` додає до trace child. Замість назви C API `fork()` у системному trace може бути видно `clone()` або інший kernel interface: бібліотечний API та конкретний системний виклик не зобов'язані мати однакові назви.

## 9. `wait()` та exit status

```sh
gcc -Wall -Wextra wait_basic.c -o wait_basic
./wait_basic
```

Child вивів повідомлення, зачекав дві секунди й завершився зі статусом `42`. Parent заблокувався у `wait()` до завершення child, після чого перевірив `WIFEXITED(status)` і отримав код через `WEXITSTATUS(status)`. Значення `42` є exit status, а не PID. Порядок виводу child та parent залежав від планування й буферизації.

## 10–12. `exec()` і launcher

```sh
gcc -Wall -Wextra exec_basic.c -o exec_basic
./exec_basic
```

Після повідомлення `Before exec` запустилася програма `echo`. Успішний `execlp()` не повернувся: він замінив program image поточного процесу. PID залишився тим самим, нового процесу `exec()` не створив. У разі помилки `execlp()` повертає керування, після чого виконується `perror()`.

Збереження PID було перевірено за допомогою runner і shell-команди, яка друкує PID:

```sh
gcc -Wall -Wextra process_runner.c -o process_runner
./process_runner /bin/sh -c 'printf "After exec PID=%s\n" "$$"'
```

У цьому запуску Codespaces PID child до `exec` і PID, надрукований shell після `exec`, збіглися.

Роботу `fork()` разом з `exec()` та `waitpid()` було продемонстровано на прикладі:

```sh
gcc -Wall -Wextra fork_exec.c -o fork_exec
./fork_exec
```

```text
fork()  → створити child process
exec()  → замінити програму, яку виконує child
wait()  → дочекатися завершення child і забрати його статус
```

Програму `launcher.c` було скомпільовано й перевірено з командами `date`, `whoami` та `uname`:

```sh
gcc -Wall -Wextra launcher.c -o launcher
./launcher date
./launcher whoami
./launcher uname
```

Launcher приймає назву однієї програми, запускає її в child і чекає на завершення. Також було перевірено обробку відсутнього аргументу та помилку запуску програми. Приклад відтворює частину роботи shell: створення child, запуск іншої програми та очікування її завершення.

## 13–14. Стани процесу та zombie

За допомогою `states.c` було досліджено стан процесу під час очікування таймера:

```sh
gcc -Wall -Wextra states.c -o states
./states
```

Стан процесу було прочитано з іншого terminal командами:

```sh
ps -o pid,ppid,state,cmd -p PID
cat /proc/PID/status
```

Під час `sleep()` процес перебував у стані sleeping/waiting і не витрачав CPU на активне виконання. Після спостереження процес було зупинено.

Для дослідження zombie було скомпільовано й запущено `zombie.c`:

```sh
gcc -Wall -Wextra zombie.c -o zombie
./zombie
```

Parent надрукував PID child і перейшов у `sleep()`, не викликаючи `wait()`. Поки parent працював, стан child було перевірено командами:

```sh
ps -o pid,ppid,state,cmd -p CHILD_PID
cat /proc/CHILD_PID/status
```

У запуску в Codespaces child мав стан `Z (zombie)`. Завершений child не виконував інструкцій і не використовував CPU, запис про нього зберігався, доки parent не забрав exit status через `wait()`. Було встановлено, що додавання `wait(NULL)` до parent усуває zombie після завершення child. Демонстраційний процес було завершено після спостереження.

## 15. Кількість процесів після кількох `fork()`

У `fork_count.c` було виконано два послідовні виклики `fork()`:

```sh
gcc -Wall -Wextra fork_count.c -o fork_count
./fork_count
```

Кожен успішний `fork()` виконується всіма наявними процесами, тому після двох викликів було отримано чотири процеси й чотири рядки `PID=...`. Для трьох послідовних викликів модель дає вісім процесів. Загальна модель для `n` успішних викликів — `2^n`.

```text
Початковий процес
├── після першого fork: 2 процеси
└── після другого fork: 4 процеси
```

## Фінальне завдання: `process_runner`

Файл `process_runner.c` було реалізовано для запуску програми та її аргументів:

```sh
gcc -Wall -Wextra process_runner.c -o process_runner
./process_runner date
./process_runner uname -a
```

Runner вивів PID parent, створив child, надрукував PID/PPID child, запустив програму через `execvp()`, дочекався її через `waitpid()` і показав результат завершення. Було перевірено обробку помилок `fork`, `execvp` та `waitpid`. Для нормального завершення child було показано його exit status; для завершення через signal передбачено виведення номера signal. Exit status child повертається як код завершення самого runner.

Для зіставлення коду з системними викликами команду `./process_runner /bin/true` було запущено під `strace` у Codespaces. Trace містив такі суттєві операції (PID тут скорочено):

```text
clone(..., SIGCHLD, ...) = CHILD_PID
execve("/bin/true", ["/bin/true"], ...) = 0
wait4(CHILD_PID, [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], ...) = CHILD_PID
```

У trace створення процесу відобразилося як `clone`, запуск нового program image — як `execve`, а очікування parent — як `wait4`. Точні syscall-и та формат trace можуть залежати від системи.

## Контрольні питання

1. **Чим program відрізняється від process?** Program — executable-файл; process — запущений екземпляр із власним станом та адресним простором.
2. **Що таке PID?** Ідентифікатор процесу, призначений ОС.
3. **Що таке PPID?** PID батьківського процесу.
4. **Чому один executable може мати декілька PID?** Кожен окремий запуск створює окремий процес.
5. **Яку роль виконує `/proc/PID`?** Надає інтерфейс для спостереження за інформацією про процес у Linux.
6. **Що таке system call?** Контрольований запит програми до kernel для виконання операції ОС.
7. **Чим function call відрізняється від system call?** Звичайний виклик функції виконує код у процесі; системний виклик переходить до kernel. Library function може всередині зробити нуль, один або кілька системних викликів.
8. **Яку роль виконує `strace`?** Показує системні виклики та сигнали, які спостерігаються під час роботи програми.
9. **Що робить `fork()`?** Створює child process як продовження поточного процесу.
10. **Скільки процесів існує після одного успішного `fork()`?** Два: parent і child.
11. **Чому `fork()` повертає `0` у child?** Це дає child змогу відрізнити свою гілку виконання від parent.
12. **Що отримує parent як результат `fork()`?** PID child; у разі помилки `fork()` повертає `-1`.
13. **Чи мають parent і child спільну змінну після `fork()`?** Ні, вони мають незалежні логічні адресні простори; зміни одного процесу не змінюють змінну іншого.
14. **Чому однакові virtual addresses не означають спільну змінювану пам'ять?** Однакові числові адреси в різних процесах можуть відображатися на різні фізичні сторінки.
15. **Що робить `exec()`?** Замінює program image поточного процесу на нову програму.
16. **Чи створює `exec()` новий process?** Ні.
17. **Що відбувається з PID після успішного `exec()`?** Він залишається тим самим.
18. **Для чого потрібен `wait()`?** Щоб дочекатися завершення child та забрати його результат завершення.
19. **Що таке exit status?** Невеликий код, який процес передає при нормальному завершенні. Для `wait` його читають через `WEXITSTATUS` після перевірки `WIFEXITED`.
20. **Що таке zombie process?** Завершений child, чий статус ще не забрав parent.
21. **Чи zombie продовжує виконувати інструкції?** Ні, він уже завершив виконання.
22. **У чому різниця між Ready, Running та Waiting?** Ready очікує CPU, Running виконується на CPU, Waiting заблокований до події, наприклад таймера чи завершення child.
23. **Чому порядок parent і child після `fork()` не гарантований?** Їх планує scheduler ОС, тобто порядок залежить від розкладу та взаємодії процесів.
24. **Як `fork → exec → wait` пов'язаний із shell?** Shell створює child, у ньому запускає команду через `exec`, а parent зазвичай чекає завершення команди.

## Короткий висновок

У лабораторній роботі було досліджено відмінність між executable та його запущеними процесами, використано PID/PPID і `/proc`, а за допомогою `strace` спостережено системний виклик `write`. Експериментально встановлено, що `fork()` створює child з окремим адресним простором, `exec()` замінює програму без зміни PID, а `wait()` синхронізує parent із завершенням child та дає змогу забрати його статус. На цій основі було реалізовано launcher і `process_runner`, що відтворюють базову модель запуску команди shell.
